# 价格追踪系统任务卡死 — 诊断与修复

## 1. 根因诊断

**任务卡死的核心链路：**
```
21:00 调度器启动 → 串行爬取22个机型
  → 21:37 完成21个
  → 22:28 「小米手环10」请求发出
  → 爬虫层阻塞（无超时 or 超时过长）
  → 主线程/事件循环被卡住
  → 23:00 截止机制本身依赖同一线程/进程 → 无法触发
  → progress.json 写入逻辑在"全部完成后"才执行 → 未写入
  → 日报生成依赖 progress 完成状态 → 未触发
```

**最可能原因（按概率排序）：**

| 排序 | 原因 | 表现 |
|------|------|------|
| ① | 爬虫请求无超时/超时过长 | HTTP连接挂起，永不返回 |
| ② | 目标页面结构变更导致解析死循环 | 无限重试或等待元素 |
| ③ | 截止机制与任务在同一进程 | 截止代码根本没机会执行 |
| ④ | progress写入时机设计为"批次完成后" | 单任务卡死→整批状态丢失 |

---

## 2. 系统设计缺陷

```
缺陷1: 单点阻塞 → 全局瘫痪
  任务串行执行 or 虽并发但共享阻塞资源
  一个任务卡死 = 整个调度停摆

缺陷2: 截止机制不独立
  23:00 强制截止逻辑跑在同一进程
  被卡住的 await 阻塞了截止检查

缺陷3: 进度写入粒度太粗
  只在全部完成后写 progress.json
  没有逐任务写入 → 无法断点恢复

缺陷4: 无外部看门狗
  没有独立进程/cron 监控任务存活状态
  系统无法自愈
```

---

## 3. 具体解决方案

### 3.1 单任务超时隔离

```python
import asyncio

TASK_TIMEOUT = 300  # 单任务最大5分钟

async def crawl_with_timeout(model_name: str) -> dict | None:
    try:
        result = await asyncio.wait_for(
            crawl_price(model_name),
            timeout=TASK_TIMEOUT
        )
        return result
    except asyncio.TimeoutError:
        log.error(f"[TIMEOUT] {model_name} 超过 {TASK_TIMEOUT}s，已强制终止")
        return None  # 返回 None，不阻塞其他任务

async def run_all_tasks(models: list[str]):
    tasks = [crawl_with_timeout(m) for m in models]
    # gather 保证即使单个失败也不影响其他
    results = await asyncio.gather(*tasks, return_exceptions=True)

    for model, result in zip(models, results):
        if isinstance(result, Exception):
            log.error(f"[EXCEPTION] {model}: {result}")
        save_progress(model, result)  # 逐个写入
```

### 3.2 独立截止看门狗（进程级隔离）

**截止机制必须跑在独立进程，不能和爬虫共享事件循环：**

```python
# watchdog.py — 独立进程运行
import time, subprocess, json, sys

DEADLINE = "23:00"
PID_FILE = "crawler.pid"
PROGRESS_FILE = "progress.json"

def check_and_kill():
    while True:
        now = time.strftime("%H:%M")
        if now >= DEADLINE:
            progress = json.load(open(PROGRESS_FILE))
            pending = [m for m, s in progress.items() if s["status"] == "running"]

            if pending:
                pid = int(open(PID_FILE).read().strip())
                log(f"[WATCHDOG] 截止时间到，{len(pending)} 个任务未完成，强制终止 PID {pid}")
                subprocess.run(["kill", "-9", str(pid)])

                # 标记超时任务
                for m in pending:
                    progress[m]["status"] = "timeout"
                json.dump(progress, open(PROGRESS_FILE, "w"))

                # 用已有数据生成日报
                generate_daily_report(partial=True)
            break

        time.sleep(30)  # 每30秒检查一次
```

**启动方式：**
```bash
# crontab
0 21 * * * python crawler.py & echo $! > crawler.pid && python watchdog.py
```

### 3.3 逐任务进度持久化

```python
import json, fcntl
from pathlib import Path

PROGRESS_FILE = Path("progress.json")

def save_progress(model: str, result: dict | None):
    """每完成一个任务立即写入，支持断点恢复"""
    with open(PROGRESS_FILE, "r+") as f:
        fcntl.flock(f, fcntl.LOCK_EX)  # 并发安全
        progress = json.load(f)

        progress[model] = {
            "status": "done" if result else "failed",
            "price": result.get("price") if result else None,
            "timestamp": time.time(),
        }

        f.seek(0)
        json.dump(progress, f, ensure_ascii=False, indent=2)
        f.truncate()
        fcntl.flock(f, fcntl.LOCK_UN)
```

## 4. 兜底恢复机制

```
层级1: 单任务超时 (5min)
  └─ asyncio.wait_for → 跳过该任务，记录 failed

层级2: 批次截止 (23:00)
  └─ 独立 watchdog 进程 → kill 爬虫 → 用已有数据出日报

层级3: 断点恢复 (次日或手动)
  └─ 读 progress.json → 只重跑 status != "done" 的任务

层级4: 日报降级生成
  └─ 即使只有部分数据，也生成日报并标注缺失项
```

**断点恢复入口：**

```python
async def resume_failed():
    progress = json.load(open("progress.json"))
    failed = [m for m, s in progress.items() if s["status"] in ("failed", "timeout", "running")]

    if not failed:
        log("无需恢复")
        return

    log(f"恢复 {len(failed)} 个任务: {failed}")
    results = await asyncio.gather(*[crawl_with_timeout(m) for m in failed])

    for model, result in zip(failed, results):
        save_progress(model, result)
```

## 总结

**核心修复四件事：**
1. 给每个请求加硬超时
2. 进度逐条写入
3. 看门狗独立进程跑
4. 日报支持部分数据降级生成

**关键：看门狗进程隔离 — 截止逻辑和爬虫共进程是这次事故的根本原因**
