# 扣子提交规范

本文档用于约束扣子修改本仓库时的 Git 流程和文件边界。

## 一、固定分支

扣子只允许提交到：

```bash
local/dev
```

禁止直接提交到：

```bash
main
```

`main` 只保留稳定可运行版本，由本地确认后再合并。

## 二、每次修改前必须同步

开始改代码前，先执行：

```bash
git checkout local/dev
git pull --rebase origin local/dev
```

如果出现冲突，先解决冲突，再继续修改。禁止用强制覆盖远程或强推来解决冲突。

## 三、允许提交的内容

允许提交：

- `config/` 下的配置文件
- `scripts/` 下的有效脚本
- `docs/` 下的技术文档
- `templates/` 下的模板文件
- `扣子原价格爬取功能/` 下的日程、工具、sub-agent 模板
- `白天异动检测/` 下的静态配置和 README

## 四、禁止提交的内容

禁止提交：

- `.env`
- `记忆文件/`
- `data/` 运行时数据
- `每日备份/`
- `logs/`
- 生成的日报图片、趋势图片
- `.zip`、`.tar.gz` 等导出包
- `cloud_pc_daily.json`
- `2026_*/` 每日输出目录

这些文件只允许本地保留，不进入 Git。

如果需要把运行现场发给本地排查，不要直接提交原始 `data/`、`logs/`、`每日备份/`。请生成脱敏排障快照：

```bash
python3 scripts/collect_debug_snapshot.py --name latest
git add debug_snapshots/latest
git commit -m "chore: add sanitized debug snapshot"
git push origin local/dev
```

`debug_snapshots/` 可以提交，因为它由脚本生成，会复制关键运行数据并脱敏敏感字段。

## 五、废弃入口禁止恢复

以下两个脚本已经废弃，不能再放回 `scripts/` 根目录：

```text
scripts/price_crawler.py
scripts/run_daytime_scan.py
```

它们只允许保留在：

```text
scripts/deprecated/
```

当前正确执行链路是：

```text
Calendar -> sub-agent -> search_web/mobile_use -> Python 后处理
```

Python 脚本只负责验证、记录、归档、生成日报和渲染图片，不负责替代 `search_web` 或 `mobile_use` 直接爬取。

## 六、提交前检查

提交前必须执行：

```bash
git status --short
```

如果看到以下内容，不要提交：

```text
data/
每日备份/
logs/
*.png
*.zip
*.tar.gz
scripts/price_crawler.py
scripts/run_daytime_scan.py
```

如果看到 `debug_snapshots/latest/`，可以提交；如果看到原始 `data/`、`每日备份/`、`logs/`，不要提交。

如误加入运行数据，执行：

```bash
git restore --staged data 每日备份 logs
```

如误恢复废弃脚本，删除根目录副本：

```bash
git rm scripts/price_crawler.py scripts/run_daytime_scan.py
```

## 七、提交格式

每次提交并推送 `local/dev` 前，必须同步更新版本号：

- 统一版本文件：`config/release.json`
- 当前项目版本基线从 `2.5.0` 开始；不要再使用 `1.x.x` 版本号
- 必须递增 `version`，并更新 `updated_at`
- 如果改动涉及日程、调度、日报链路，也要同步更新 `config/schedule.json` 的 `version` 和 `updated_at`
- 推送完成后，回复时必须同时给出：版本号、commit id、修改范围

版本号规则：

```text
主版本.次版本.修订号
```

- 配置/文档小改：修订号 +1，例如 `2.5.1 -> 2.5.2`
- 日程、数据流、推送链路调整：次版本 +1，例如 `2.5.x -> 2.6.0`
- 破坏性大改或执行模型变化：主版本 +1，例如 `2.x.x -> 3.0.0`

示例：

```json
{
  "version": "1.5.2",
  "branch": "local/dev",
  "updated_at": "2026-04-30T12:00:00+08:00"
}
```

提交信息使用以下格式：

```text
类型: 简短说明
```

常用类型：

- `feat`: 新功能
- `fix`: 修复问题
- `docs`: 文档更新
- `config`: 配置调整
- `chore`: 仓库维护、备份、清理

示例：

```bash
git add .
git commit -m "config: update 21:00 mobile_use quota"
git push origin local/dev
```

## 八、推荐完整流程

```bash
git checkout local/dev
git pull --rebase origin local/dev

# 修改文件

git status --short
git add .
git status --short
python3 -m json.tool config/release.json >/dev/null
git commit -m "类型: 本次修改说明"
git push origin local/dev
```

推送完成后，把版本号、commit id 和修改范围发回。

## 九、Coze 3.0 多 Agent 提交边界

Coze 3.0 下，本仓只允许作为“行情监控 Agent”的代码和配置事实源。提交时额外遵守：

- 只提交行情监控相关的 `config/`、`scripts/`、`docs/`、`templates/` 变更。
- 总控 Agent 文档可以保留在 `docs/`，但总控 Agent 不得拥有业务脚本执行权。
- 反卷教练相关改动必须进入独立反卷仓，不得在本仓新增或恢复反卷教练目录。
- 复合需求必须拆分为两个独立 Agent 子任务，不能在一次执行里跨仓读写。
