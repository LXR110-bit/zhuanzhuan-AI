# 行情追踪助手系统运行总规范

**版本**：v1.0  
**日期**：2026-04-28  
**优先级**：最高。若其他文档、记忆文件、提示词与本文冲突，以本文和 `config/schedule.json` 为准。

---

## 一、当前问题归因

现在出现的三个问题：

1. 播报时间不稳定
2. 日报不生成图片，直接发 Markdown
3. 汇报内容混乱、信息错位、口径错误

根因不是单个任务坏了，而是系统里同时存在多套事实源：

| 问题 | 直接表现 | 根因 |
|---|---|---|
| 播报时间问题 | 凌晨误推、10点漏推、6点/10点冲突 | `schedule.json`、流程文档、记忆文件各自定义时间 |
| 不生成图片 | 文档要求图片，但实际推 Markdown | 推送提示词没有把“图片卡片”设为硬约束 |
| 汇报混乱 | 价格、信号、建议错位 | 报告生成同时读取旧记忆、旧缓存、临时分析结果 |

## 二、唯一时间规则

系统统一使用北京时间 `Asia/Shanghai`。

### 2.1 每日正式播报

| 时间 | 动作 | 说明 |
|---|---|---|
| 04:00 | 信息源抓取 | 头条、抖音泛搜、RSS、网页搜索等 |
| 05:00 | 聚合去重 | 只产出结构化数据，不推送 |
| 05:30 | 信号分级与价格分析 | 写入统一日报 payload |
| 06:00 | 生成图片卡片 | 只生成图片，不正式播报 |
| 09:50 | 延迟检查 | 图片未完成则发延迟预警 |
| 10:00 | 正式播报 | 推送两张图片卡片 |
| 10:10/10:20/10:30 | 重试 | 最多三次 |
| 10:30后 | 截止 | 标记 missed，只发失败通知 |

**硬规则**：06:00 不是正式播报时间。任何日报正式推送必须在 10:00 之后。

### 2.2 三条原始业务线

原系统不是单链路，也不是所有脚本全量执行。保留三条业务线：

| 业务线 | 时间 | 入口 | 说明 |
|---|---|---|---|
| 市场追踪日报 | 06:00 生成，10:00 推送 | `scripts/init_daily_status.py` 等日报链路 | 06:00 不推送，只生成数据和图片 |
| 白天异动检测 | 07:30 / 12:00 / 17:30 | Calendar -> sub-agent -> `search_web`/`mobile_use` | A层8个机型轻量检测 |
| 晚间全量检测 | 21:00 | Calendar -> sub-agent -> `search_web`/`mobile_use` | A+B层22个机型深度爬取 |
| 云电脑扫描 | 每2小时 | Calendar -> sub-agent -> `search_web` | 轻量价格扫描，输出到日报 |

### 2.3 白天任务

白天任务分为两类，不能混在一起跑：

**白天异动检测**：会刷新价格缓存，属于轻量检测任务。

```text
07:30 / 12:00 / 17:30
```

当前可执行白天异动检测入口是 Calendar 日程拉起 sub-agent，日程描述使用：

```text
扣子原价格爬取功能/日程描述模板_20260429.md#一、白天异动检测
扣子原价格爬取功能/工具调用模板_20260429.md
```

sub-agent 完成 `search_web`/`mobile_use` 后，再调用 Python 后处理脚本做验证、归档和报告生成。

白天异动检测完成后会刷新：

```text
data/price_cache.json
data/trend_history/
data/daily_report_payload.json
data/report_cards/
data/daytime_scan_status.json
```

**晚间全量检测**：21:00 执行 A+B 层22个机型深度爬取，输出图片卡片日报和告警。

```text
扣子原价格爬取功能/日程描述模板_20260429.md#二、晚间全量检测
扣子原价格爬取功能/工具调用模板_20260429.md
```

`scripts/deprecated/run_daytime_scan.py` 是废弃入口，不再作为日程入口使用。

**日间增量巡检**：轻量资讯巡检，不等于价格扫描，也不等于正式日报推送。

```text
10:00 / 14:00 / 18:00
```

其中 10:00 首先执行正式日报推送；推送完成后如需巡检，只做轻量补充巡检。S级信号可即时告警，A级信号汇入晚报或下一次报告，B级仅入缓存。

**云电脑扫描**：独立于白天异动检测，每2小时执行一次。

```text
08:00 / 10:00 / 12:00 / 14:00 / 16:00 / 18:00 / 20:00 / 22:00
```

当前可执行入口：

```bash
python3 scripts/run_cloud_pc_scan.py run --slot HH:MM
```

云电脑扫描输出 `cloud_pc_daily.json`，再汇入 `data/daily_report_payload.json`。

### 2.4 数据验证和异动判定

价格进入日报前必须先经过验证层：

```text
data/price_cache.json -> scripts/price_data_validator.py -> data/validation_report.json
```

硬规则：

- 价格变动超过 20%：写入预警。
- 价格变动超过 30%：标记为需要人工确认。
- `null` 显示为 `—`，必须标注缺失原因。
- PC硬件在闲鱼官方回收价和爱回收价缺失是正常覆盖率问题，不允许推测填充。
- S级必须同时满足：≥3算法、跌幅 >30%、置信度 >90%。

资讯信号进入日报前必须经过：

```bash
python3 scripts/news_signal_filter.py
```

硬规则：

- 每条行情资讯必须有发布时间。
- 超过7天的资讯不进入日报。
- 7天窗口内按 URL 或“来源+标题”去重。
- 去重历史写入 `data/news_signal_dedupe_history.json`，避免同一行情跨天重复播报。

价格播报进入日报前必须经过：

```bash
python3 scripts/price_daily_recorder.py
```

硬规则：

- 每日记录价格：闲鱼自由市场价格、闲鱼官方回收价格、爱回收价格；不再使用拼多多。
- 价格监控日报只展示价格和日环比，不混入资讯长文。
- 每日价格卡片采用“6个品类各2个代表机型”展示；底层 `price_cache.json`、`daily_price_records/` 继续保留全量机型，供排查和周/月趋势分析使用。
- 云手机执行模板固定为：闲鱼App搜索 `{search_term}` -> 回收服务 -> 轻微使用痕迹（9成新）-> 官方回收价；爱回收App搜索 `{search_term}` -> 基础价 / 券后价 / 碳索家价；两个 App 均 90 秒超时。

基准线更新：

```bash
python3 scripts/update_baseline.py
```

该命令只生成 `data/baseline_update_proposal.json`。人工确认后，才允许执行：

```bash
python3 scripts/update_baseline.py --apply-confirmed
```

静默期：

```text
22:30 - 07:30
```

静默期内只允许写日志和缓存，不允许推送日报或普通价格报告。S级紧急告警是否绕过静默期，需要人工确认后再开。

## 三、唯一输出规则

### 3.1 日报必须是图片

日报、周报、月报必须推图片卡片，禁止推完整 Markdown。

每日固定两张：

1. 市场追踪日报
2. 价格监控日报

模板来源：

```text
templates/双卡片模板.md
templates/daily_report_card.md
```

### 3.2 Markdown 的允许范围

Markdown 只允许用于三类短消息：

1. S级即时告警
2. 延迟预警
3. 图片/推送失败通知

不得用 Markdown 长文代替日报图片。

## 四、唯一数据入口

日报生成只能读取一个结构化入口：

```text
data/daily_report_payload.json
```

推荐结构：

```json
{
  "date": "2026-04-28",
  "generated_at": "2026-04-28T06:00:00+08:00",
  "summary": {
    "one_sentence": "",
    "today_action": "",
    "data_quality": ""
  },
  "signals": {
    "S": [],
    "A": [],
    "B": []
  },
  "prices": {
    "updated_at": "",
    "rows": []
  },
  "risks": {
    "drop_alerts": [],
    "rise_alerts": [],
    "missing_data": []
  },
  "images": {
    "market_daily_card": null,
    "price_monitor_card": null
  }
}
```

禁止日报生成时直接混读：

- `记忆文件/*.md`
- 旧日报
- 旧流程文档
- 未标注更新时间的缓存价格
- `cloud-pc-monitor` 独立输出中的旧字段

这些文件只能作为背景知识，不能作为日报事实源。

## 五、固定汇报顺序

所有日报内容必须按以下顺序组织，不能临场发挥：

1. 一句话结论
2. 今日动作
3. S级信号
4. A级信号
5. 价格总览
6. 风险/异常
7. 数据质量说明

每条价格必须包含：

- 机型
- 平台
- 价格
- 价格类型
- 更新时间
- 数据状态

如果数据缺失，写“缺失原因”，不要用旧数据补齐后装作今日数据。

## 六、推送状态规则

推送前必须检查：

```text
data/push_status.json
scripts/report_guard.py before_push
```

推荐状态结构：

```json
{
  "version": "1.0.0",
  "date": "2026-04-28",
  "daily_report": {
    "expected_push_time": "10:00",
    "status": "pending",
    "attempts": 0,
    "sent": false,
    "sent_at": null,
    "image_required": true,
    "images": {
      "market_daily_card": null,
      "price_monitor_card": null
    },
    "last_error": null
  },
  "alerts": []
}
```

状态流转：

```text
pending -> image_ready -> sending -> sent
pending/image_ready/sending -> retrying
retrying -> sent
retrying -> missed
```

硬规则：

- 未到 10:00 禁止日报推送
- `sent=true` 禁止重复推送
- 图片未生成禁止发送完整日报
- 10:30 后不再补发完整日报，只发送失败通知

## 七、三个问题的修复原则

### 7.1 播报时间问题

唯一修复点：

```text
config/schedule.json
```

其他文档只描述，不作为调度真源。

### 7.2 不生成图片

推送链路必须拆成三步：

```text
结构化日报 payload -> 图片卡片 -> 图片推送
```

跳过图片生成直接推送，即视为失败。

当前可执行图片生成入口：

```bash
python3 scripts/render_report_cards.py
```

输出位置：

```text
data/report_cards/{YYYY-MM-DD}_market_daily_card.png
data/report_cards/{YYYY-MM-DD}_price_monitor_card.png
```

当前完整日报链路：

```bash
python3 scripts/init_daily_status.py
python3 scripts/generate_daily_report_payload.py
python3 scripts/render_report_cards.py
python3 scripts/report_guard.py before_push
python3 scripts/send_daily_report.py
```

调试时可用：

```bash
python3 scripts/send_daily_report.py --dry-run
```

### 7.3 汇报混乱

所有报告先生成结构化 payload，再从 payload 渲染图片。

不要让 LLM 一边找资料、一边补价格、一边写结论、一边排版。这样必然错位。
